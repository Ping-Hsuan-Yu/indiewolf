## B. 錯誤清單（依影響嚴重度排序）

### E1（中高｜第 4 章唯一實質修正）— 287KB render-blocking CSS 的成因假說不成立；真因已查明：next/font 的 CJK @font-face 宣告

- **報告位置**：§4.3 L3、§4.4 修正 #5、第 5 章 PERF-5、§7.2「靜態推斷未驗證」第一條。
- **原文**：「成因需 bundle analyzer 確認（admin 樣式外洩到公開 bundle？Tailwind content glob 過廣？）」；修法「bundle analyzer 定位 + 切分 admin 與公開 CSS，確保 Tailwind content 範圍正確」。
- **為何錯**：兩個候選假說皆不成立，且成因不需 bundle analyzer，curl 五個 CSS 檔即可查明（本次已查明）。實測組成（壓縮後/原始）：
  - `6f498b71….css` **247KB/693KB＝Noto Serif TC 的 735 條 `@font-face`**（7 個 weight × 105 個 unicode-range 切片；`font-family:Noto Serif TC` 735 次、每 weight 恰 105 次）
  - `49f7f7a8….css` 36KB/102KB＝**Chocolate Classical Sans（admin 專用字型）109 條 @font-face——admin「字型」確實外洩到公開頁**（因 `app/font.ts` 單一模組五種字型同檔宣告），但 admin「樣式」沒有
  - `36e7e2….css` 0.8KB＝Noto Sans（也是 admin 字型）；`512ce0….css` 1KB＝Abhaya Libre + Gambetta
  - `58588e….css` **10KB/56KB＝真正的 Tailwind 樣式，大小完全正常**；五檔中 `sidebar`/admin class 出現 0 次
  - 即 287KB 中 **~277KB（96%）是字型宣告 CSS**，樣式僅 ~10KB。
- **建議改法**：
  1. §4.3 刪除 L3 的兩個假說，改寫為已確認事實：「render-blocking CSS 5 檔 294KB（壓縮），其中 96% 為 next/font 產生的 CJK @font-face 宣告——Noto Serif TC 7 weights 佔 247KB、admin 專用的 Chocolate Classical Sans/Noto Sans 因 `app/font.ts` 單一模組而洩入公開頁佔 37KB；Tailwind 樣式本身僅 10KB、正常」。L3 與 L4 合併為同一根因（信心：高，已實測）。
  2. §4.4 將 #5 與 #7 合併為一項：「字型瘦身＝CSS 瘦身」——刪 Noto Serif TC 用不到的 weight（7→實際使用數，每刪一個 weight 約 -35KB 壓縮 CSS）＋把 `app/font.ts` 拆成 public/admin 兩個模組使 admin 字型不進公開頁（再 -37KB）。成本低（非中）、影響中-高（直接砍掉 LCP 關鍵路徑上 ~200KB+ render-blocking 資源），排序應上移到 #3 附近。bundle analyzer 一項可整個刪除。
  3. PERF-5、§7.2 對應條目、§6.2 第 12 項前後文同步改。

### E2（中）— MAINT-3 描述的失敗機制與程式碼實況不符

- **報告位置**：§3.2 MAINT-3、第 5 章 MAINT-3 列。
- **原文**：「新手若對 create 沿用 `if (!res.success)` 會拿到 `undefined.success` 崩潰」。
- **為何錯**：實查 `createManga`（admin/manga.ts）與 `createIllustration`（admin/illustration.ts:53）成功時**都 `return { success: true }`**、失敗時 throw——呼叫端在成功路徑拿得到 `res.success`，在失敗路徑根本拿不到回傳值（promise reject），不存在「undefined.success」的情境。create 其實是「throw 與 success 物件混合」的第三種慣例，比報告描述的更混亂。
- **證據**：`app/_actions/admin/manga.ts:56-58`（`revalidatePath…; return { success: true }`）、`app/_actions/admin/illustration.ts:53`。
- **建議改法**：混用慣例的結論保留（成立），失敗情境改寫為：「create 失敗時 throw（呼叫端未包 try/catch 則錯誤直接冒泡）、成功時又回 `{ success: true }`；update/delete 失敗時回 `{ success: false }` 不 throw（呼叫端若只用 try/catch 永遠 catch 不到失敗）——兩種心智模型都各有一半函式不適用」。

### E3（低中）— AVAIL-1 的「顯示 not-found.tsx 的 404」細節未必成立

- **報告位置**：§3.1 AVAIL-1、執行摘要 Top 5 #2。
- **原文**：「任一公開頁都顯示 `not-found.tsx` 的『404』」。
- **為何存疑**：Next 的 not-found boundary 包的是該 segment 的 **children**，不包 layout 自身；`notFound()` 從 `app/[locale]/layout.tsx`（root layout）拋出時，很可能落到 Next **內建** 404 頁而非 `app/[locale]/not-found.tsx`（本專案無全域 root layout，也放不了 `app/not-found.tsx`）。此為依 Next 文件語意的推斷，未動態驗證（不宜對 production 演練 DB 斷線）。**核心結論不變**：使用者看到的仍是「404 找不到頁面」而非錯誤頁，故障語意錯位的判斷完全成立。
- **來源**：https://nextjs.org/docs/app/api-reference/functions/not-found （「terminates rendering of the route segment in which it was thrown」；boundary 渲染於 segment 之內）。
- **建議改法**：改寫為「顯示 404（自訂 not-found.tsx 或 Next 內建 404，取決於 boundary 解析；兩者對使用者都是『頁面不存在』）」，或在 v2 補一次本機實驗（dev 環境斷網跑 `next dev` 觀察）再定稿。

### E4（低）— 「Supabase 新專案預設開啟註冊」無官方文件佐證

- **報告位置**：執行摘要 Top 5 #1、§3.3 SEC-1、§6.1 第 1 項。
- **原文**：「若 Supabase Email 註冊為開啟（新專案預設開）」。
- **為何有問題**：官方文件（https://supabase.com/docs/guides/auth/general-configuration ）只描述開關行為（「If this config is disabled, only existing users can sign in」），**未明言預設值**。第三方文章普遍以「預設開啟」為前提撰寫關閉教學，社群認知一致，但報告把它寫成斷言。
- **建議改法**：改為「一般認知為新專案預設開啟（官方文件未明言預設值），故此設定**必須**人工確認」——報告本來就要求人工確認，只需把斷言軟化為有出處的常識判斷。SEC-1 的條件性 Critical 定位不變。

## C. 遺漏清單（僅列既定範圍內該有而沒有的）

### O1（重要）— 第 4 章未說明 Speed Insights 是什麼、資料從哪來

整章以「Speed Insights 分數偏低」為題，卻沒有一句話定義它。零背景模型無從判斷「為什麼台灣使用者的體感會決定分數」。**補法**：§4 開頭加 2-3 句——「Vercel Speed Insights 是第一方 RUM：由掛在三個 layout 的 `@vercel/speed-insights` script 從真實訪客瀏覽器回報 Core Web Vitals，儀表板預設顯示 p75，綜合為 Real Experience Score；**不是** Google CrUX。因此分數直接反映實際訪客（台灣為主）打到 iad1 動態頁的體驗，這正是本章把根因指向地理錯置的前提。」來源：https://vercel.com/docs/speed-insights 、 https://vercel.com/docs/speed-insights/metrics 。這同時把 §4.2 開頭「量測來源地：香港/台灣一側」的邏輯閉合。

### O2（重要）— 修正 #1（vercel.json regions）缺生效條件與方案限制

`regions` 設定**只對加入後的新 deployment 生效**，既有部署不變（需 push 觸發重建或手動 redeploy）；Hobby 方案僅能選**單一** region（多 region 需 Pro/Enterprise），本專案方案未查——但單一 `icn1` 在任何方案都合法，故修法不變、只需補條件說明。零背景模型若只改檔不重新部署，會誤判「修了沒效」。來源：https://vercel.com/docs/functions/configuring-functions/region 、 https://vercel.com/changelog/hobby-customers-can-now-select-their-preferred-region-for-serverless 。

### O3（已代為補上）— L3 成因被列為「待 bundle analyzer」，實為零成本可查明

curl 五個 CSS 檔＋grep font-family 十分鐘內可得決定性答案（見 E1），屬「既定範圍內該分析而沒分析」。v2 直接寫入 E1 的實測結果即可，無需保留「待確認」狀態。

### O4（小）— admin 字型洩入公開頁未被任何一章發現

`app/font.ts` 五種字型同一模組，公開 layout 只用三種，但 admin 專用的 Chocolate Classical Sans（36KB 壓縮）與 Noto Sans 的 @font-face CSS 仍進了公開頁 critical path。這是 E1 的副產品，v2 併入 E1 的改寫即可，不需獨立條目。

（依任務範圍聲明，深度 a11y 與離線/慢網為刻意排除項，未列。）

## D. 改寫建議（結構性/表達性）
