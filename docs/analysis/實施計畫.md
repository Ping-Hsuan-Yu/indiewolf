## 0. 目標與成功定義

產出一份**自足**（self-contained）的專案分析報告，讓一個對此 repo 零背景的模型（Opus 4.8 或 Sonnet 5）讀完後能：
1. 理解專案的目的、架構、資料流、功能全貌
2. 掌握目前的品質狀態（可用性、可維護性、安全性、效能）與具體證據（檔案:行號）
3. 直接依報告中的「問題清單 + 優先序」規劃下一步改善，不需重新掃 repo

成功判準：
- 報告每個 claim 都有證據（檔案:行號、指令輸出、或外部來源 URL）
- Speed Insights 劣化有根因分析與可執行修正方案（含預期影響）
- 通過 Phase 3 獨立 Fable 評論者的查證（無重大事實錯誤）

## 0.5 已查證的 repo 基線事實（盤點 agent 產出，2026-07-11）

- Stack：Next.js 16（proxy.ts 取代 middleware）、React 19、Tailwind 4、Supabase（SSR + service-role admin client）、Cloudinary、next-intl、Vercel（含 @vercel/analytics 與 @vercel/speed-insights）
- 規模：113 個 TS/TSX 檔、10,196 行；app/ 68 檔（其中 28 檔 'use client'）；components/ 30 檔（23 個 shadcn UI + 7 個公開元件）
- 路由：公開站 7 個 page（home/about/illustration/[year]/manga/[status]/project/[slug]）＋ admin（login + dashboard + 4 個 CRUD 區）；**0 個 route handler**
- Server actions：11 檔（admin 4 + public 6 + common），`serverActions.bodySizeLimit: '500mb'`
- 資料庫：10 張表（about_profiles, home_kv_frames, illustration_works, manga_works, manga_images, nav_items, project_works, project_images, social_links, ui_translations），3 個 migration
- i18n：zh（預設）/ en；**翻譯不走 JSON，每次由 `ui_translations` 表讀取**（`i18n/request.ts:9`、`app/_actions/public/ui-translation.ts`）
- 測試：完全不存在（無框架、無 script、無測試檔）
- 文件：docs/ 僅 todo.md 與 quotation.md（報價單）；無專案 CLAUDE.md
- 開發狀態：最後 commit 2026-03-09（已閒置約 4 個月）；git status 乾淨（僅未追蹤的 .mcp.json）

## 1. 偏誤控管（本計畫的前提約束）

已查證的偏誤來源與對策：

| 偏誤來源 | 風險 | 對策 |
|---|---|---|
| 專案級 CLAUDE.md | 不存在（已確認）| 無需處理，但 subagent prompt 中明示「不要假設有專案慣例文件」 |
| 主對話的全域 CLAUDE.md + ponytail persona | 極簡主義傾向可能讓分析偏向「刪東西」而低估必要投資 | 分析類 subagent 一律 fresh context（新開 Agent 天然不帶主對話上下文與 persona hook）；prompt 保持中性，不夾帶「精簡」「YAGNI」等價值判斷詞 |
| repo 內 commit message / docs 的自我描述 | 開發者自述意圖 ≠ 實際行為 | 要求 subagent 以程式碼實際行為為準，文件自述只能作為「意圖」引用並標註 |
| 主對話轉述時的資訊壓縮失真 | 中間摘要層層失真 | 各分析 agent 直接落檔（sections/*.md），彙整 agent 讀原始落檔而非讀主對話轉述 |
| LLM 自評偏誤（自己寫的自己審） | 高估完成度 | Phase 3 評論者為全新 Fable agent，且被明確指示以「反駁/挑錯」立場審查並用網路查證外部事實 |

## 3. Phase 2 工作包與模型分工

分工原則（依兩模型特性）：
- **Sonnet 5**：吞吐型工作——大面積讀檔、盤點、事實蒐集、結構化描述。快且便宜，適合「把事實擺出來」。
- **Opus 4.8**：判斷型工作——根因分析、安全審查、架構評價、優先序裁決。慢但深，適合「說出事實代表什麼」。
- 所有 agent 均為 fresh context（新開 Agent），prompt 附上必要背景（repo 路徑、stack 摘要、落檔路徑），不轉述主對話的任何評價。

**污染防線（審查必改 1）**：WP prompt 只給「repo 路徑、任務範圍、落檔路徑、驗收條件」，**不給** §0.5 基線事實、不給任何嫌疑犯假說（如 i18n-DB、bodySizeLimit）、不給其他 WP 的存在與產出。基線事實僅供主對話驗收比對用。

| # | 工作包 | model | 內容 |
|---|---|---|---|
| WP1 | 架構與資料流（管「怎麼流」） | sonnet | App Router 結構、rendering 策略（static/dynamic/ISR/client）、Supabase 資料流、i18n 架構、proxy/middleware 行為、路由錯誤邊界（error/loading/not-found 是否存在、DB 掛掉時公開頁行為）、部署拓撲 |
| WP2 | 功能與資料模型（管「有什麼」） | sonnet | 功能清單（公開站 + admin）、DB schema（migrations + supabase MCP）、server actions 清單、外部服務整合（Cloudinary）、SEO/metadata（generateMetadata、OG、sitemap、robots） |
| WP3 | 程式碼品質與可維護性 | opus | 重複碼、型別品質、錯誤處理、元件邊界、命名一致性、依賴健康度、測試缺口 |
| WP4 | 安全 | opus | Supabase RLS 政策（migrations SQL 為準，supabase MCP get_advisors 佐證）、server action 授權檢查、admin 路由保護、secrets 處理 |
| WP5 | 效能與 Speed Insights 根因 | opus | **先取實測數據**：找出 production URL（vercel MCP / repo 設定），跑 PageSpeed Insights API 或 `npx lighthouse`（mobile+desktop）、`curl -w` 量 TTFB 多次、vercel MCP 查 region/runtime logs；讀 WP6 的 build 輸出取得 route 級 rendering/bundle 資訊（不自己重跑 build）；程式碼面檢查 LCP/CLS/INP/TTFB 各自的候選成因（圖片、字型、blocking、client 面積、資料瀑布、每請求外部呼叫成本）；產出：每個差的指標 → 根因（或根因假說＋驗證方法）→ 修正方案（依預期影響排序） |
| WP6 | 建置健康度 | sonnet | 實跑 lint、tsc --noEmit、`npm run build`，完整輸出存 build-logs/，回報摘要；Node/Next 版本相容性 |

執行順序（審查必改 3）：WP1-WP4 + WP6 平行派出；**WP5 等 WP6 完成後啟動**（避免兩個 build 互撞，並讓 WP5 直接消費 build 輸出）。各自落檔 scratchpad/sections/NN-*.md。
Speed Insights 真實欄位數據若無法取得（MCP 無此端點、使用者未提供儀表板數據），WP5 成功判準降級為「根因假說＋每個假說的驗證方法」（審查意見 14）。

## 4. Phase 2 彙整 → 分析報告 v1

派一個 fresh **Opus 4.8** 彙整 agent：讀 sections/ 全部落檔 + 實施計畫，產出 `分析報告-v1.md`。
結構要求：
1. 執行摘要（一頁內：專案是什麼、健康狀態總評、Top 5 問題）
2. 專案全貌（架構圖文字版、功能清單、資料模型）
3. 品質評估（可用性/可維護性/安全/效能，各含證據）
4. Speed Insights 根因分析與修正方案（獨立章節，含優先序與預期影響）
5. 問題總表（嚴重度 × 修復成本矩陣）
6. 建議下一步（給接手模型的行動建議）
7. 附錄：分析方法、涵蓋範圍與已知盲點

## 5. Phase 3 獨立評論（Fable 5）

派 fresh **Fable 5** agent（model: fable, general-purpose）：
- 立場：挑錯者。查證規則（審查意見 8）：**Top 5 問題與 Speed Insights 章節 100% 逐 claim 查證**（開檔核對 檔案:行號、重跑可重現的指令）；其餘 claim 隨機抽 20%
- 外部事實用 WebSearch/context7 查證（如 Next 16 行為、Vercel Speed Insights 計分方式、Supabase 最佳實務）
- 範圍外項目（審查意見 13）：深度 a11y、離線/慢網行為屬刻意排除，不得以「遺漏」為由要求補入
- 產出 `修正方案.md`：錯誤清單（v1 哪裡錯/過時/無證據）、遺漏清單、改寫建議

## 6. Phase 4 修正 → v2

裁決採機械準則（審查意見 9，避免主對話 persona 偏誤）：**修正意見有證據（檔案:行號、指令輸出、可信來源 URL）→ 接受；無證據或僅風格偏好 → 駁回並記錄理由**。依裁決修訂產出 `分析報告-v2.md`，關鍵 claim 附 2-3 行原文摘錄＋commit SHA（審查意見 10）。
最後派 haiku read-back 驗收：章節完整、無空段落、無殘留 TODO、所有 檔案:行號 格式正確。全部完成後將四份文件寫入 repo docs/analysis/。

## 7. 升降級與失敗處理

依 dispatch.md 第 5 節：sonnet 同一工作包連錯 2 次升 opus；opus 連錯 2 次停下回報使用者。
任何 agent 無法完成驗收 → 如實回報卡點，不編造。build/lint 若因環境問題跑不動，在報告中標註「未驗證」而非略過。
