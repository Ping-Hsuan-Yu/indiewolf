## 1. 執行摘要

**這是什麼專案**：插畫家 Lin ChaoYu 的雙語（zh 預設 / en）個人作品集網站。公開站展示四類內容——首頁主視覺（home KV）、關於頁、插畫（illustration，依年份）、漫畫（manga，依連載狀態）、專案（project）；後台 `/admin` 是單語 zh-TW 的 CRUD 管理介面，透過 Supabase Auth 登入。圖片全部託管於 Cloudinary，翻譯文案不走 JSON 檔而是每次請求從 `ui_translations` 資料表現撈。部署於 Vercel（已由 Vercel MCP 確認，非推測）。最後一次 commit 為 2026-03-09，已閒置約 4 個月。

**整體健康評語**：功能可運作、結構意圖清晰（server actions 分層、授權邊界一致、RLS 全表啟用），但工程紀律不足且基礎架構有一項嚴重地理錯置。核心問題可歸為四束：（a）一個條件性 Critical 安全缺口——授權只驗「是否登入」而無 admin 白名單，其真實嚴重度取決於一項需人工確認的 Supabase 設定；（b）多處「故障被靜默吞掉」的設計，使資料庫斷線在公開站表現為 404、使查詢失敗表現為空白頁且 log 無錯誤；（c）Speed Insights 分數偏低的主因是 function（美東）與 DB（首爾）跨洲錯置，加上首頁被硬設為永不快取；（d）「複製貼上取代抽象 + 零測試」的可維護性債，每新增一種內容類型都會再複製一輪既有缺陷。migration 與線上 schema 已漂移，若有人依 migrations 重建資料庫，公開站會直接壞掉。

**Top 5 問題**（依實際後果排序，完整清單見第 5 章）：

| # | 問題 | 一句話根因 | 嚴重度 |
|---|---|---|---|
| 1 | 授權模型「登入即管理員」，若 Supabase 開放自助註冊則後台全開 | 三層權限檢查都只驗 `!user`（是否登入），無 admin id/email 白名單；一般認知為 Supabase Email 註冊新專案預設開啟（官方文件未明言預設值，故須人工確認），若為開啟，任何人可用 client bundle 內公開的 anon key 註冊取得 session，經 service-role 繞過 RLS 刪改所有內容 | **Critical（條件性，需人工確認）** |
| 2 | 資料庫斷線時，**所有**公開頁顯示「404 找不到頁面」而非錯誤頁 | `getUiMessages` 查詢失敗靜默回傳 `{}`，root layout 見空訊息物件即呼叫 `notFound()`，把「DB 離線」偽裝成「頁面不存在」 | 高 |
| 3 | 動態頁 TTFB 冷啟 3.1s、熱狀態 ~1.7s（靜態頁的 7–12 倍） | serverless function 在美東 `iad1`、DB 在首爾 `ap-northeast-2`、使用者在台灣，每個動態請求跨太平洋來回；首頁/about/project 又被 `force-dynamic` 設成永不快取 | 高 |
| 4 | 依 migrations 重建資料庫會使公開站的漫畫/插畫「作品查詢」全部壞掉（插畫年份頁的 `get_distinct_years` 已在 migration，倖存） | 8 個 PostgREST `public_id` 函式與 4 個孤兒 enum 只存在於線上資料庫、不在任何 migration；公開站查詢用 `select('*, src:public_id')` 直接依賴它們，且因吞錯（見 #5）實際表現為空白頁而非報錯 | 高 |
| 5 | 公開資料層無型別 + 靜默吞錯，故障全程無任何偵錯訊號 | `lib/supabase.ts` 的 client 未帶 `<Database>` 泛型，且 public getter 多數不讀 `error`；schema/欄位改動時 TS 不報錯、執行期回空集合、server log 也無錯誤，直到畫面壞掉才會發現 | 高 |

## 3. 品質評估

### 3.1 運行時可用性

**AVAIL-1（高）— DB 斷線時所有公開頁顯示 404 而非錯誤/維運頁。** 這是全站最嚴重的可用性設計缺陷，證據鏈三步：
1. `app/_actions/public/ui-translation.ts:18-21`：`getUiMessages` 查詢出錯時靜默降級，不拋例外——
   ```ts
   if (error) { console.error(...); return {} }
   ```
2. `app/[locale]/layout.tsx:66-75`：root layout 拿到訊息後，只要是空物件就 `notFound()`——
   ```ts
   if (!messages || Object.keys(messages).length === 0) { notFound() }
   ```
3. 此 layout 是**所有**公開頁共用的 root，`loadMessages()` 在渲染任何子頁前執行。

結果：DB 離線 → `getUiMessages` 回 `{}` → root layout 判定「訊息不存在」→ 任一公開頁都顯示 404（自訂 `not-found.tsx` 或 Next 內建 404，取決於 boundary 解析——`notFound()` 從 root layout 拋出時，Next 的 not-found boundary 包的是該 segment 的 children、不包 layout 自身，故實際落點未動態驗證；但兩者對使用者呈現的都是「頁面不存在」，核心結論不變）。維運人員與使用者會誤判為「內容被刪/設定錯誤」而非「資料庫離線」，兩種需完全不同應變的狀況呈現成同一畫面。後台則相反：`admin/(main)/layout.tsx:28-35` 的 `auth.getUser()` 在斷線時回 `user: null`，被當成「未登入」→ redirect 到 login，同樣是訊息語意錯位（但不 crash）。

**AVAIL-2（高）— 公開資料 getter 靜默吞錯，使用者看到空白頁、log 無錯誤。** `app/_actions/public/*` 多數查詢連 `error` 都不解構，失敗直接回空集合。`public/illustration.ts:17-24`：
```ts
const { data } = await supabase.from('illustration_works').select(...)...
console.log(data)
return data || []
```
`about.ts`、`manga.ts` 同樣只取 `data`。Supabase 故障、RLS 擋掉、schema 改名時前台不報錯、不提示、server log 也看不到錯誤（error 根本沒被讀）。此問題與 AVAIL-1 同源（皆為「靜默降級」慣例），由架構章與品質章各自獨立發現、交叉印證。

**AVAIL-3（中）— 後台無錯誤邊界、全站無 loading 骨架。** 全 repo 只有 `app/[locale]/error.tsx` 與 `not-found.tsx` 兩個邊界檔（`find` 掃描確認），`app/admin/**` 底下完全沒有 `error.tsx`/`not-found.tsx`——後台拋未捕捉例外會落到 Next 預設錯誤畫面。無任何 `loading.tsx`，動態頁伺服器渲染完成前無 loading UI。

**AVAIL-4（中）— 上傳成功但 DB 寫入失敗 → Cloudinary 孤兒檔。** 所有 create 都是「先傳 Cloudinary → 再寫 DB」，DB 失敗時（如 `manga.ts:51-54`）不刪已上傳圖；刪除流程「先刪 DB → 再刪圖」，`deleteCloudinaryImage` 失敗也不回滾且吞錯（`lib/cloudinary.ts:23-25` `catch { console.error }` 不 rethrow）。長期累積孤兒檔，佔配額費用，無對帳機制。

### 3.2 可維護性

整體判斷：**功能可運作、結構意圖清晰，但工程紀律不足**。問題不在架構選型，而在「複製貼上取代抽象」「型別與錯誤處理不當回事」「零測試」三者疊加。四個內容領域（manga/illustration/project/about）是高度相似的平行模組，卻採「整段複製再微調」。

**MAINT-1（高）— Cloudinary 上傳區塊逐字重複 9 次。** `file → arrayBuffer → Buffer → new Promise 包 upload_stream` 一字不差出現於 `manga.ts:25-35,260-271,380-390`、`project.ts:43-53,199-209`、`about.ts:79-89,138-148,203-213`、`illustration.ts:23-33`，唯一差異是 `folder` 字串。後果：要加逾時/重試/檔案驗證或換 SDK 必須同時改 9 處，漏改即行為分歧。

**MAINT-2（高）— 公開資料層完全喪失 DB 型別。** `lib/supabase.ts:6` 未帶泛型：
```ts
export const supabase = createClient(supabaseUrl, supabaseAnonKey)
```
對比 `utils/supabase/admin.ts` 的 `createClient<Database>(...)`。因此所有 `public/*` 查詢回傳無型別，才需在每個 getter 硬轉 `as MangaWork[]`（`public/manga.ts:42,64`）。schema 改動 TS 不報錯，執行期回 undefined 欄位——與 AVAIL-2 疊加使前台故障完全無訊號（Top 5 #5）。

**MAINT-3（高）— create 拋例外、update 回物件，兩種錯誤慣例混用。** create 類（`createManga` `manga.ts:22,53`、`createIllustration`、`createProject`、`getAdminAboutPageData`）用 `throw`；其餘 update/delete/toggle 用 `return { success: false, error }`。呼叫端因函式而異（`AddMangaSheet.tsx` 用 try/catch，`MangaDetailForm.tsx:407-414` 檢查 `res.success`）。實查 `createManga`（`admin/manga.ts:56-58`）、`createIllustration`（`admin/illustration.ts:53`）成功時都 `return { success: true }`，失敗時 throw——create 其實是「throw 與 success 物件混合」的第三種慣例：成功路徑呼叫端拿得到 `res.success`，失敗路徑則是 promise reject、未包 try/catch 會直接冒泡，不存在「`undefined.success`」的情境。反之對 update/delete 若只用 try/catch 永遠 catch 不到失敗（因為它們失敗時回物件、不 throw）。兩種心智模型都各有一半函式不適用，是最容易寫出無聲 bug 的地方。

### 3.3 安全

方法：靜態原始碼分析 + Supabase MCP 線上交叉比對（security advisors、RLS 狀態、`auth.users` 統計），僅讀取、未對 production 做任何寫入或攻擊性操作。

**核心結論**：整個後台的安全邊界可濃縮成一句——「攻擊者能不能拿到這個 Supabase 專案的任一個已登入 session？」授權模型是「只要 authenticated 就等於 admin」，沒有角色、沒有 email 白名單。程式碼紀律其實不錯：12 個 admin mutation actions 一致透過 `getAuthorizedAdminClient()` 取得 service-role client（該函式先 `auth.getUser()` 驗登入）；public actions 一律 anon client，無一誤用 admin client；secrets 未進 client bundle、未進 git。真正風險集中在「authenticated == admin」這個假設，以及它是否被 Supabase 專案層級的「開放註冊」設定架空。

**SEC-1（Critical，條件性，需人工確認）— 授權只驗登入、無 admin 白名單。** 三層防護（`proxy.ts` middleware redirect、`admin/(main)/layout.tsx:33` redirect、`common.ts:28` action 層）判準都只是 `if (!user)`：
```ts
// app/_actions/common.ts:28
if (authError || !user) throw new Error('Unauthorized')
```
沒有一層比對 user id/email 是否屬於 admin。若 Supabase Auth 的「Allow new users to sign up」為開啟（**Supabase 新專案預設開啟**），任何人可用 client bundle 內公開的 anon key 直接呼叫該專案 `/auth/v1/signup` 註冊帳號取得 session，通過全部三層檢查，呼叫 `deleteMangaWork`/`deleteProject` 等 action，經 service-role 繞過 RLS 刪光或竄改所有內容。線上 `auth.users` 目前 2 位、皆已 confirm、建立於 2026-03-05~06（像刻意建立的管理帳號），但這不代表註冊已關閉，只代表尚無人濫用。**此設定不在資料庫、無法透過 MCP 讀取——需使用者至 Supabase Dashboard → Authentication → Providers → Email 確認「Allow new users to sign up」是否關閉。若為開啟，SEC-1 為 Critical、最優先修補。**

**SEC-2（高）— 四表 RLS policy `USING(true) WITH CHECK(true)` 對 authenticated。** `about_profiles`/`project_works`/`project_images`/`social_links` 允許 authenticated 直接讀寫（`baseline.sql:166-167,192-193,198-199,204-205`）；線上 advisor 標為 `rls_policy_always_true`（4 筆 WARN）。承 SEC-1 取得任一 session 後，攻擊者**連 server action 都不需要**，直接用瀏覽器 anon client 對這四表 insert/update/delete（例如把 social_links 的 url 改成惡意連結）。對比 manga/illustration/home_kv/nav/ui 五類只有 public 讀、無 authenticated 寫入 policy（寫入完全靠 service-role），後者反而是較安全的設計。安全章的「四表過寬」與功能章的「六表缺寫入 policy」是同一份 RLS 的一體兩面，合起來涵蓋全 10 表，無矛盾。

**SEC-3（中）— 檔案上傳無型別/大小驗證 + `bodySizeLimit: '500mb'`。** 四類 upload action（`manga.ts:25/246/366`、`project.ts:43/191`、`illustration.ts:23`、`about.ts:70/194`）只檢查「檔案存在 / `size > 0`」，不檢查 MIME/副檔名/大小上限，直接 `arrayBuffer()`→`Buffer`→上傳。`next.config.mjs:24` 允許單請求送 500MB body，且整檔讀進記憶體；搭配並發（`uploadMangaImages` CONCURRENCY=3）易造成記憶體壓力。屬 DoS/資源濫用向量（前提同樣需 authenticated session）。文字輸入以參數化查詢寫入（無 SQL injection），輸出由 React 轉義（無 `dangerouslySetInnerHTML`），`next/image` `remotePatterns` 僅允許 `res.cloudinary.com`（無 SSRF）。

**SEC-4/5/6（低）**：Leaked password protection 未啟用（advisor `auth_leaked_password_protection` WARN，admin 可用已外洩弱密碼）；多個 SQL 函式 `search_path` 未固定（advisor `function_search_path_mutable`，因非 SECURITY DEFINER 提權面小，屬 hygiene）；`app/[locale]/error.tsx:15-17` 直接顯示 `error.message`（prod 由 Next digest 遮蔽，dev 洩內部訊息，面小）。

**已解除的疑慮**：架構章曾將「`.env` 內含正式 service-role key」列為高風險待查；安全章查證後解除——`.env` 未被 git 追蹤（`git ls-files --error-unmatch .env` not matched）、`.gitignore:76` 已排除、無 secret 洩漏到 client bundle（僅 `NEXT_PUBLIC_` 三個本就公開的值進 bundle）、tracked source 無硬編碼憑證。此為兩章交叉查證後的降級，非矛盾。

## 4. Vercel Speed Insights 根因分析與修正方案

> 量測來源地：香港/台灣一側（Vercel edge = `hkg1`）。基礎架構事實經 Vercel MCP / Supabase MCP 確認。

**Speed Insights 是什麼、分數從哪來**：Vercel Speed Insights 是第一方 RUM（Real User Monitoring）——由掛在三個 layout 的 `@vercel/speed-insights` script 從真實訪客瀏覽器回報 Core Web Vitals，儀表板預設顯示 p75，綜合為 Real Experience Score；**不是** Google CrUX。因此分數直接反映實際訪客（台灣為主）打到 `iad1` 動態頁的真實體驗，這正是本章把根因指向地理錯置的前提，也與上一段「量測來源地：香港/台灣一側」的邏輯相呼應（來源：https://vercel.com/docs/speed-insights 、 https://vercel.com/docs/speed-insights/metrics ）。

### 4.1 一句話結論

Speed Insights 分數差的**主因不在前端程式碼，而在基礎架構的地理錯置**：Vercel 的 serverless function 跑在 `iad1`（美東華盛頓），但 production DB 在首爾 `ap-northeast-2`，真實使用者與 CDN edge 在台灣/香港。每個「動態頁」請求都要跨太平洋來回兩趟（台灣 → 美東 function → 首爾 DB → 回台灣）。首頁又被硬設 `force-dynamic`，每次到訪都付這筆跨洲延遲。修正順位：**(1) function 移首爾 `icn1` → (2) 移除首頁/about/project 的 `force-dynamic` 改靜態+ISR → (3) 首頁主視覺圖片最佳化**。

### 4.2 實測數據

| 路由 | 渲染策略 | 冷啟動 | 熱狀態中位 | Vercel 快取 | Function 區域 |
|---|---|---|---|---|---|
| `/`（→307 `/zh`） | middleware | 0.26 | 0.14–0.21 | — | — |
| `/zh`（首頁） | ƒ 動態 `force-dynamic` | **3.13** | **~1.69** | MISS | `iad1` 美東 |

### 4.3 逐指標根因

**TTFB（最嚴重，且是 LCP 的地基）**
- **T1 — Function 區域錯置（iad1 美東）。信心：高。** 證據：`x-vercel-id: hkg1::iad1`、無 `vercel.json`、DB 首爾。影響：每次 DB 查詢 RTT 從同區 ~2ms 變跨洲 ~180ms。
- **T2 — 首頁/about/project 硬設 `force-dynamic`，永不快取。信心：高。** 證據：四頁皆 `export const dynamic = 'force-dynamic'`（`(home)/page.tsx:8`、`about/page.tsx:1`、`project/page.tsx:12`、`project/[slug]/page.tsx:8`）+ header `MISS`/`no-store`。內容其實是極少變動的 CMS 資料，卻每次到訪重新 SSR + 打 DB。
- **T3 — 每請求序列式 DB 瀑布，其中 `getUiMessages` 重複執行。信心：中高（機制有 next-intl 文件支持，未動態計數）。** 首頁一次請求約 4 次序列查詢：`i18n/request.ts:9` → `getUiMessages()`（第一次）；`app/[locale]/layout.tsx:46` 呼叫 `loadMessages()`、其內部（`:67-68`）再呼叫一次——這是同一次呼叫鏈，不是獨立的第二次。真正的重複來自 `NextIntlClientProvider` 由 Server Component 渲染時，若未顯式傳入 `timeZone`/`now`/`formats`，會自動繼承並重新執行一次 `i18n/request.ts` 的 request config（next-intl v4 文件行為），因此 `getUiMessages()` 實際仍會被觸發兩次；`PublicNavbar.tsx`/`Footer` 皆為 `'use client'`，其 `useTranslations()` 走 Provider 傳下的資料、本身不是觸發點。另加 `PublicNavbar.tsx:4` → `getNavItems()`；`(home)/page.tsx` → `getHomeKVFrames()`。約 4 次 × 跨洲 ~180ms 疊加成數百 ms。
- **T4 — DB 查詢無任何快取層。信心：高。** 所有 `public/*.ts` 直接 `supabase.from(...)`，未用 `unstable_cache`/`React cache()`/`revalidateTag`，每次都回源。

**LCP**
- **L1 — TTFB 太高直接墊高 LCP。信心：高。** 動態頁 LCP 起跑點就 ~1.7s。
- **L2 — 主視覺 LCP 圖未最佳化且 8 張同時 eager 載入。信心：高。** `HomeKV.tsx` 用原生 `<img src={frames[n]}>`（非 `next/image`/`CldImage`），URL 為 Cloudinary 原圖無 transform；LCP 圖 111 KB（可壓到 67 KB 或更小）+ 另 780 KB 同時搶頻寬，4G 下嚴重拖慢。
- **L3/L4（合併，同一根因：字型）— 294 KB render-blocking CSS，其中 96% 是 next/font 產生的 CJK `@font-face` 宣告。信心：高（已實測，非假說）。** 首頁 `<head>` 5 個 `<link rel=stylesheet>` 合計 294,287 B（壓縮後）。逐檔查明組成：`6f498b71….css` 247KB＝**Noto Serif TC 的 735 條 `@font-face`**（7 個 weight × 105 個 unicode-range 切片，`app/font.ts` 宣告 7 種 weight、`subsets: ['latin']` 但 CJK 字型仍需大檔）；`49f7f7a8….css` 36KB＝**Chocolate Classical Sans（admin 專用字型）109 條 @font-face——因 `app/font.ts` 單一模組同時宣告公開與 admin 字型，admin 字型也洩入了公開頁**；`36e7e2….css` 0.8KB＝Noto Sans（同樣是 admin 字型）；`512ce0….css` 1KB＝Abhaya Libre + Gambetta；`58588e….css` **10KB＝真正的 Tailwind 樣式，大小完全正常**（五檔中 `sidebar`/admin class 出現 0 次，排除「admin 樣式外洩」與「Tailwind content glob 過廣」兩個假說）。即 294KB 中 ~277KB（96%）是字型宣告、Tailwind 本身僅 10KB。全部 `display: swap`。

**CLS**
- **C1 — 列表/關於頁用無尺寸 raw `<img>`。信心：中高。** `project/page.tsx` 封面、`about/page.tsx` 個人照皆無 `width/height`/`aspect-ratio`，載入後才撐開高度。（首頁 `HomeKV` 反而用隱形 spacer 預留高度、做對了。）
- **C2 — 字型 `display: swap` 造成 FOUT 位移。信心：中。**

**INP / 主執行緒**
- **I1 — HomeKV 每 150ms setInterval 重繪。信心：中。** 首頁掛載後主執行緒每秒 ~6.7 次 re-render（切換 8 張堆疊 `<img>` 的 opacity），影響 INP 與行動裝置耗電。
- **I2 — Lightbox 全量載入。信心：低中。** `MangaGallery.tsx` 頂層 import lightbox 與其 CSS，不論是否點開都下載。
