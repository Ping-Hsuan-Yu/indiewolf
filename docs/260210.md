## Supabase RLS Policy Audit

I have inspected the RLS (Row Level Security) status of your project (`diwxkpiwnirlvngldcoi`).

### 1. Current Status (Risk Analysis)

- **RLS is Enabled**: ✅ All tables have RLS enabled (`relrowsecurity: true`). This is good.
- **Read Access**: ✅ Most tables allow public read access, which is correct for a CMS-backed website.

- **Write Access (Ref: `Authenticated ALL`)**: ⚠️ **High Risk**
    - Tables: `project_works`, `project_images`, `about_profiles`, `social_links`
    - Policy: `Enable all for authenticated users` (CMD: ALL, TO: authenticated)
    - **Risk**: Any user who logs in (if registration is open) can **Edit or Delete** data in these tables. Currently, there is no check for "Admin" status in the database policy, only "Is Logged In".

- **Write Access (Ref: Service Role)**:
    - Tables: `manga_works`, `illustration_works`, `home_kv_frames`, etc.
    - Policy: No write policies exist.
    - **Implication**: Only the "Service Role" (Admin Client) can modify these. This is why your code checks for login and then uses `createAdminClient()`. This is safer than `Authenticated ALL` but defeats the purpose of RLS.

### 2. Recommendations

#### Short-term Fix (Code Level Security)
Since you are using `getAuthorizedAdminClient()`, you are bypassing RLS. To secure this:
1. **Restrict `getAuthorizedAdminClient`**: Add a whitelist check (e.g., specific email) in this function before returning the Admin Client. This prevents a random logged-in user from invoking Admin Actions.

#### Long-term Fix (Database Level Security - Best Practice)
1. **Remove `Authenticated ALL` Policies**: These are dangerous. Change them to Read-Only for public/authenticated users.
2. **Implement Admin Role**:
    - Add a `role` field to `auth.users` metadata or a separate `admins` table.
    - Create a Policy: `auth.jwt() ->> 'email' = 'admin@yourdomain.com'` OR `auth.uid() IN (SELECT user_id FROM admins)`.
3. **Switch to Standard Client**:
    - Once RLS is fixed to allow only admins to write, you can stop using `createAdminClient()` and use `createClient()` (Standard).
    - Checks will happen at the Database level, which is the most secure architecture.
